# 线程池压测（bench）

四类指标：**吞吐/伸缩**、**空闲唤醒开销**、**提交路径开销**、**不均衡负载**，
另外附带与「锁粒度优化前」版本的 A/B 对照。

## 怎么跑

```bash
# 构建（含示例程序 example 和压测程序 bench）
cmake -S . -B build && cmake --build build -j

# 旧版对照程序（锁粒度优化 e0de867 之前的实现，导出后需重新 cmake）
bash bench/prepare_baseline.sh && cmake -S . -B build && cmake --build build -j

# 跑全套（固定 CPU、多轮取中位数、结果写 bench/results/*.csv）
bash bench/run_bench.sh

# 专门的 A/B 交替对照（抵消环境漂移，见下文「可信度」）
bash bench/compare_ws.sh

# perf 热点剖析（多数环境默认禁止非 root 使用 perf，建议在自己机器上跑）
sudo sysctl -w kernel.perf_event_paranoid=0 && bash scripts/perf.sh
```

## 测量约定

- 压测前把日志级别提到 `FATAL`：`FixedThreadPool` 每个任务都会 `LOG_INFO`，不关掉测的就变成日志吞吐了。
- 任务体只捕获一个指针，`std::function` 走小对象优化，避免压测代码自己产生堆分配。
- 等待「全部任务完成」用条件变量精确唤醒，不用轮询。
- `taskset -c 0-7` 绑核；多轮取中位数并报告离散度。

## 本机环境（结果只在此环境下有意义）

VMware 虚拟机，8 vCPU（宿主 i7-12700H），Ubuntu + g++ 13.3 `-O2`。

## 结果（2026-10-07 实测）

### 1. 吞吐量

**空任务、单提交线程、100 万任务**（此时瓶颈在提交端，程序会自动标注）

| 线程池 | 吞吐(tasks/s) | 提交(ms) | 离散度 |
|---|---|---|---|
| fixed | 1,441,411 | 693.4 | 27.7% |
| cached | 1,220,112 | 818.8 | 13.8% |
| workstealing | 1,259,698 | 793.7 | 48.9% |

> 离散度 28%~49%，池间差异落在噪声范围内，**不建议**用这一组比较池的性能。

**5µs 任务、4 个提交线程、40 万任务**（执行端成为瓶颈）

| 线程池 | 吞吐(tasks/s) | 总耗时(ms) | 提交(ms) | 排空(ms) | 离散度 |
|---|---|---|---|---|---|
| fixed | 734,440 | 544.6 | 260.1 | 286.9 | 6.5% |
| cached | 707,079 | 565.7 | 299.0 | 257.5 | 4.3% |
| workstealing | **915,224** | 437.1 | 149.6 | 280.0 | 10.7% |

同样的对比在旧版二进制里也成立（fixed 754,302 / workstealing 915,596），
**工作窃取池比固定池高约 21%~25%，且提交耗时只有固定池的 58%**（149.6ms vs 260.1ms，每队列独立锁 + `notify_one` 的效果）。

### 2. 伸缩性（5µs 任务、10 万任务、4 提交线程）

| 线程池 | 1 线程 | 2 线程 | 4 线程 | 8 线程 | 8 线程加速比 / 效率 |
|---|---|---|---|---|---|
| fixed | 157,872 | 329,741 (2.09×) | 570,740 (3.62×) | 615,583 | **3.90× / 48.7%** |
| workstealing | 164,244 | 327,616 (1.99×) | 654,048 (3.98×) | 892,859 | **5.44× / 68.0%** |

固定池在 8 线程时效率掉到 48.7%（共享队列 + 每次入队 `notify_all` 唤醒全部消费者），
工作窃取池 68.0%。

### 3. 空闲唤醒与空闲 CPU（8 线程空转 3 秒，不提交任何任务）

| 线程池 | 唤醒(次/秒/线程) | 被动切换(次/秒) | 空闲 CPU 时间(ms) | CPU 占用/线程 |
|---|---|---|---|---|
| fixed | 10.0 | 0.0 | 7.43 | 0.031% |
| cached | 10.0 | 0.0 | 7.81 | 0.033% |
| workstealing | **502.9** | 49.7 | 275.09 | **1.146%** |

工作窃取池空闲时每线程每秒唤醒 **503 次**，是固定池（10 次，队列等待用 100ms 超时）的 **50 倍**，
空闲 CPU 占用高 **37 倍**。原因是 `WSyncQueue` 的等待超时是 1ms，且窃取路径要对最多 7 个队列
依次做 1ms 等待（`SyncQueue_2.hpp:143`、`WorkStealingThreadPool.hpp:91`）。

> 旧版同样严重（685.4 次/秒/线程、1.564%），所以这不是「优化引入的问题」，而是两版都存在、
> 且优化只让它降了约 27%（685→503）。

### 4. 提交路径开销（提交 20 万次、队列容量 20 万、8 线程）

| 线程池 | 提交方式 | 每次提交(ns) | 堆分配(次/提交) |
|---|---|---|---|
| fixed | AddTask | 563.3 | 0.06 |
| fixed | submit(future) | **1851.9** | **5.04** |
| cached | AddTask / submit | 664.7 / 2008.0 | 0.06 / 5.06 |
| workstealing | AddTask / submit | 608.4 / 2110.8 | 0.06 / 5.06 |

`submit()`（要返回 `future`）比 `AddTask` 贵 **2.9~3.5 倍**，堆分配次数多约 **84 倍**
（`make_shared<packaged_task>` + `std::bind` + `std::function` 包装；`AddTask` 的 0.06 主要是 deque 分块摊还）。
这解释了为什么纯空任务场景里吞吐被提交端限制在 120~140 万 tasks/s。

### 5. 不均衡负载与「优化前后」

负载：2 万个任务，每 8 个任务插入一个 200µs 长任务；由于任务按轮转分配到各队列，
**长任务会全部落到同一条队列**。总工作量 500ms，8 线程理想耗时 62.5ms。

| 场景 | fixed | cached | workstealing |
|---|---|---|---|
| skewed（长任务扎堆） | 79.3ms (78.8%) | 85.0ms (73.5%) | **406.5ms (15.4%)** |
| uniform-long（均匀长任务） | 639.5ms (78.2%) | 672.7ms (74.3%) | 681.4ms (73.4%) |
| uniform-short（纯调度） | 12.7ms | 12.8ms | 14.0ms |

**关键结论：长任务扎堆时，工作窃取池反而比固定池慢 5.1 倍**（406.5ms vs 79.3ms）。
固定池是共享队列、天然均衡；工作窃取池受制于「探测空队列要等 1ms 超时」+「一次只窃取一个任务」，
长任务无法被快速分摊出去（各线程任务数 1945/2709 看似均衡，但工作量极不均衡）。

**A/B 交替对照**（`bench/compare_ws.sh`，5 轮交替运行两个二进制）：

| 场景 | 当前 WS | 旧版 WS | WS/fixed 当前 | WS/fixed 旧版 | 比值改善 |
|---|---|---|---|---|---|
| skewed | 389.1ms | 507.2ms | 4.48 | 6.22 | **27.9%** |
| uniform-long | 732.2ms | 655.4ms | 1.19 | 1.03 | -15.5% |
| uniform-short | 19.1ms | 5.2ms | 1.93 | 0.36 | -430.6% |

只有 **skewed 场景的改善（约 28%）是稳定可复现的**：整套跑测里同一场景是 406.5 vs 512.1ms（29%），
两次结果一致。另外两个场景的符号在两次运行之间会翻转，属于噪声，**不能作为结论**。

## 可信度说明（重要）

**可以放心引用的**（两次运行方向一致、机制清晰）：

1. 5µs 任务、8 线程：工作窃取池约 **91.5 万 tasks/s**，比固定池（约 73.4~75.4 万）高 **21%~25%**。
2. 8 线程伸缩：工作窃取池 **5.44×（68% 效率）**，固定池 **3.90×（48.7%）**。
3. 空闲唤醒：工作窃取池 **503 次/秒/线程**，固定池 **10 次/秒**（50 倍）；空闲 CPU 占用 1.15% vs 0.031%。
4. 提交开销：`submit()` **1852ns + 5.04 次堆分配**，`AddTask` **563ns + 0.06 次**（2.9~3.5 倍 / 84 倍）。
5. 长任务扎堆场景：工作窃取池比固定池慢 **5.1 倍**（这是设计问题，不是优化引入的）。
6. 优化前后（不均衡场景、比值归一化后）：**约 28% 的改善**，不是提交信息里写的 65%。

**不能当结论的**：

- 空任务吞吐的池间差异（离散度 28%~49%，超出差异本身）。
- `uniform-long` / `uniform-short` 的新旧对比（两次运行符号相反）。
- 绝对数字的横向比较（他人机器、物理机、不同 CPU 频率都会不同）。

**为什么会有噪声**：虚拟机 + 8 vCPU，单次测量窗口只有 10ms~700ms，而每次进程启动都要新建/销毁
一整套线程池。要拿到更硬的数字，需要：加长测量窗口（更大 `--tasks`、更多 `--repeat`）、
在空闲的物理机上跑、或把 `--pool` 分开跑减少相互干扰。

**作者提交里那两个说法**（"负载不均吞吐提升 65%、空转率降低 40%"）：本次实测**没有复现到同等幅度**——
不均衡场景约 +28%，空闲唤醒约 -27%。这不代表作者当时的数据是错的（场景、机器都不同），
但你要写进简历的数字应该是**你自己这台机器上跑出来的**。

## 建议的简历句式（数字都来自上面「可以放心引用」那一节）

- 用 C++ 实现四种线程池（固定/缓存/工作窃取/定时），自建压测程序量化指标：8 线程下工作窃取池
  约 **91.5 万 tasks/s**，较固定池（约 73.4 万）高 **约 25%**，8 线程并行效率 **68%**（固定池 48.7%）。
- 通过压测定位到工作窃取池的两个真实开销：空闲时每线程每秒 **503 次无效唤醒**（固定池 10 次）、
  空闲 CPU 占用高 **37 倍**；以及长任务扎堆时吞吐仅为固定池的 **1/5**。
- 用 `git show` 导出优化前版本做 A/B 对照压测（交替运行 + 比值归一化消除环境漂移），
  确认工作窃取队列重构在不均衡场景下带来 **约 28%** 的性能改善。
- 量化提交路径：`submit()` 每次 **1852ns / 5 次堆分配**，是 `AddTask`（563ns / 0.06 次）的 3.3 倍，
  据此定位提交端为纯调度场景的瓶颈。
