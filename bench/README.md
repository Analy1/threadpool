# 线程池压测（bench）

四类指标：**吞吐/伸缩**、**空闲唤醒开销**、**提交路径开销**、**不均衡负载**，
外加**定时器精度**，以及与「锁粒度优化前」版本的 A/B 对照。

## 怎么跑

```bash
# 构建（含示例程序 example 和压测程序 bench）
cmake -S . -B build && cmake --build build -j

# 旧版对照程序（锁粒度优化 e0de867 之前的实现，导出后需重新 cmake）
bash bench/prepare_baseline.sh && cmake -S . -B build && cmake --build build -j

# 跑全套（固定 CPU、多轮取中位数、结果写 bench/results/*.csv）
bash bench/run_bench.sh

# 版本 A/B 交替对照（抵消环境漂移，见下文「可信度」）
bash bench/compare_ws.sh

# perf 热点剖析（多数环境默认禁止非 root 使用 perf，建议在自己机器上跑）
sudo sysctl -w kernel.perf_event_paranoid=0 && bash scripts/perf.sh
```

## 测量约定

- 压测前把日志级别提到 `FATAL`：`FixedThreadPool` 每个任务都会 `LOG_INFO`，不关掉测的就变成日志吞吐了。
- 任务体只捕获一个指针，`std::function` 走小对象优化，避免压测代码自己产生堆分配。
- 等待「全部任务完成」用条件变量精确唤醒，不用轮询。
- `taskset -c 0-7` 绑核；多轮取中位数并报告离散度。
- 定时器场景会**自动放大目标延迟**（避免被创建耗时污染）、把一次性定时器的目标时间**逐个错开 1ms**
  （避免几百个同时到期时，量到的其实是 epoll 线程串行处理的排队时间）。

## 本机环境（结果只在此环境下有意义）

VMware 虚拟机，8 vCPU（宿主 i7-12700H），Ubuntu + g++ 13.3 `-O2`。

## 结果（2026-10-07 16:45 那一轮实测）

### 1. 吞吐量

**空任务、单提交线程、100 万任务**（瓶颈在提交端，程序会自动标注）

| 线程池 | 吞吐(tasks/s) | 提交(ms) | 离散度 |
|---|---|---|---|
| fixed | 2,049,879 | 483.3 | 17.9% |
| cached | 1,513,909 | 659.1 | 33.5% |
| workstealing | 2,383,158 | 419.1 | 47.3% |

> 离散度 18%~47%，池间差异落在噪声范围内，**不建议**用这一组比较池的性能。

**5µs 任务、4 个提交线程、40 万任务**（执行端成为瓶颈）

| 线程池 | 吞吐(tasks/s) | 总耗时(ms) | 提交(ms) | 排空(ms) | 离散度 |
|---|---|---|---|---|---|
| fixed | 716,197 | 558.5 | 294.1 | 243.3 | 27.3% |
| cached | 739,282 | 541.1 | 305.4 | 235.7 | 5.8% |
| workstealing | **1,139,881** | 350.9 | 143.4 | 193.2 | 10.6% |

另一次跑测（同日更早）为 fixed 734,440 / workstealing 915,224（+25%）。两次都显示
**工作窃取池吞吐最高，优势来自提交路径**：4 个提交线程下它提交耗时只有固定池的一半左右
（143.4ms vs 294.1ms，每队列独立锁 + `notify_one`）。

### 2. 伸缩性（5µs 任务、10 万任务、4 提交线程）

| 线程池 | 1 线程 | 2 线程 | 4 线程 | 8 线程 | 8 线程加速比 / 效率 |
|---|---|---|---|---|---|
| fixed | 175,584 | 335,057 (1.91×) | 565,592 (3.22×) | 664,243 | **3.78× / 47.3%** |
| workstealing | 154,162 | 302,209 (1.96×) | 551,250 (3.58×) | 939,419 | **6.09× / 76.2%** |

固定池在 8 线程时效率掉到 47.3%（共享队列 + 每次入队 `notify_all` 唤醒全部消费者），
工作窃取池 76.2%。这一条在两次跑测中一致（另一次：3.90× / 5.44×）。

### 3. 空闲唤醒与空闲 CPU（8 线程空转 3 秒，不提交任何任务）

| 线程池 | 唤醒(次/秒/线程) | 被动切换(次/秒) | 空闲 CPU 时间(ms) | CPU 占用/线程 |
|---|---|---|---|---|
| fixed | 9.8 | 0.0 | 5.84 | 0.024% |
| cached | 10.0 | 0.0 | 11.30 | 0.047% |
| workstealing | **661.0** | 59.0 | 418.62 | **1.744%** |

工作窃取池空闲时每线程每秒唤醒 **661 次**，是固定池（9.8 次，队列等待用 100ms 超时）的 **67 倍**，
空闲 CPU 占用高约 **70 倍**。原因是 `WSyncQueue` 的等待超时是 1ms，且窃取路径要对最多 7 个队列
依次做 1ms 等待（`SyncQueue_2.hpp`、`WorkStealingThreadPool.hpp`）。

> 旧版同样严重（790.4 次/秒/线程、1.921%），所以这不是「优化引入的问题」，
> 而是两版都存在、且那次优化只让它降了约 20%~27%。

### 4. 提交路径开销（提交 20 万次、队列容量 20 万、8 线程）

| 线程池 | 提交方式 | 每次提交(ns) | 堆分配(次/提交) |
|---|---|---|---|
| fixed | AddTask | 202.0 | 0.06 |
| fixed | submit(future) | 1580.3 | **5.02** |
| cached | AddTask / submit | 675.0 / 2546.8 | 0.06 / 5.06 |
| workstealing | AddTask / submit | 1089.8 / 2130.6 | 0.06 / 5.06 |

**堆分配次数是最稳的一条**：`submit()`（要返回 `future`）每任务约 **5 次**，`AddTask` 约 **0.06 次**
（相差约 80 倍），来自 `make_shared<packaged_task>` + `std::bind` + `std::function` 包装。
耗时差（约 1.6~2.5 µs vs 0.2~1.1 µs）受调度影响波动较大，不宜当作精确倍数引用。

### 5. 不均衡负载

负载：2 万个任务，每 8 个任务插入一个 200µs 长任务；由于任务按轮转分配到各队列，
**长任务会全部落到同一条队列**。总工作量 500ms，8 线程理想耗时 62.5ms。

| 场景 | fixed | cached | workstealing |
|---|---|---|---|
| skewed（长任务扎堆） | **72.7ms（86.0%）** | 80.4ms（77.8%） | 427.1ms（14.6%） |
| uniform-long（均匀长任务） | 555.1ms（90.1%） | 590.1ms（84.7%） | 643.9ms（77.7%） |
| uniform-short（纯调度） | 7.0ms | 21.7ms | 9.1ms |

**关键结论：长任务扎堆时，工作窃取池比固定池慢 5.9 倍**（另一次跑测为 5.1 倍）。
固定池共享队列、天然均衡；工作窃取池受制于「探测空队列要等 1ms 超时」+「一次只窃取一个任务」，
长任务无法被快速分摊（各线程任务数 2052/2671 看似均衡，但**工作量**极不均衡）。

### 6. 定时器精度与开销（ScheduledThreadPool：timerfd + epoll）

| 指标 | 实测 |
|---|---|
| 创建一个定时器 / 取消 | 33.2 µs / 3.0 µs |
| 一次性定时器延迟误差（目标 49ms、300 个、目标错开 1ms） | P50 242 µs、P90 2301 µs、P99 5.2 ms |
| 周期性间隔误差（10ms 周期、观察 2 秒、196 次触发） | P50 18.8 µs、P99 9.2 ms |
| 平均间隔 − 目标间隔（长期漂移） | +205 µs |

创建一个定时器要 33~81 µs（timerfd_create + timerfd_settime + epoll_ctl 三次系统调用，
虚拟机里系统调用偏贵）；P50 精度在百微秒级，P99 的毫秒级尾巴来自虚拟机调度与到期事件的串行处理。

## 与「锁粒度优化前」版本的 A/B 对照

`bench/prepare_baseline.sh` 用 `git show e0de867^:` 导出旧版 `SyncQueue_2.hpp` 与
`WorkStealingThreadPool.hpp` 到 `bench/baseline/`，编出第二个二进制 `bench_baseline`，
两个二进制跑同一套压测代码（`bench/compare_ws.sh` 交替运行并用同轮内比值归一化）。

| 场景 | WS/fixed 当前 | WS/fixed 旧版 | 比值改善 |
|---|---|---|---|
| skewed（第 1 次 A/B） | 4.48 | 6.22 | **27.9%** |
| skewed（第 2 次 A/B） | 4.85 | 5.21 | **6.9%** |
| uniform-long | 1.19 / 1.22 | 1.03 / 1.15 | -15.5% / -6.1% |
| uniform-short | 1.93 / 1.50 | 0.36 / 0.60 | -430% / -149% |

**结论（重要）**：只有「长任务扎堆」场景显示优化后更好，但两次交替对照给出的幅度是 **27.9% 和 6.9%**，
不稳定；另外两个场景的量测符号会翻转，**不能作为结论**。
提交 `e0de867` 的信息里写的是「负载不均场景吞吐量提升 65%、空转率降低 40%」，
本次实测没有复现到该幅度（不均衡场景约 7%~28%，空闲唤醒约 20%~27%）。

> 对比时**必须**用 `compare_ws.sh` 的比值归一化：本机上同一份 `fixed` 池代码在先后两次跑测之间
> 都可能差 10%~30%（见上表 uniform-short 两次结果相反），直接比绝对时间会把环境漂移算成优化收益。

## 可信度说明（重要）

**可以放心引用的**（两次跑测方向一致、机制清晰）：

1. 5µs 任务、8 线程：工作窃取池 **91.5 万~114 万 tasks/s**，比固定池（约 72~75 万）高 **25%~60%**。
2. 8 线程伸缩：工作窃取池 **5.4×~6.1×（68%~76% 效率）**，固定池 **3.8×~3.9×（47%~49%）**。
3. 空闲唤醒：工作窃取池 **503~661 次/秒/线程**，固定池 **约 10 次/秒**（50~67 倍）；空闲 CPU 占用 1.1%~1.7% vs 0.02%~0.03%。
4. 提交开销：`submit()` 每任务约 **5.0 次堆分配**，`AddTask` 约 **0.06 次**（约 80 倍）。
5. 长任务扎堆：工作窃取池比固定池慢 **5.1~5.9 倍**（设计问题，非优化引入）。
6. 优化前后：不均衡场景改善 **约 7%~28%**（未复现提交信息里的 65%）。

**不能当结论的**：

- 空任务吞吐的池间差异（离散度 18%~47%，超出差异本身）。
- `uniform-long` / `uniform-short` 的新旧对比（两次交替对照符号相反）。
- `submit()` vs `AddTask` 的**耗时**倍数（分配次数稳定，耗时受调度影响）。
- 绝对数字的横向比较（他人机器、物理机、不同 CPU 频率都会不同）。

**为什么会有噪声**：虚拟机 + 8 vCPU，单次测量窗口 10ms~700ms，且每个进程都要新建/销毁一整套线程池。
要拿到更硬的数字：加长测量窗口（更大 `--tasks`、更多 `--repeat`）、在空闲物理机上跑、或把各池分开跑减少相互干扰。

## 建议的简历句式（数字都来自上面「可以放心引用」那一节）

- 用 C++ 实现四种线程池（固定/缓存/工作窃取/定时），自建压测程序做横向对比：
  8 线程、5µs 任务下工作窃取池约 **114 万 tasks/s**（固定池 71.6 万），8 线程并行效率 **76.2%**
  （固定池 47.3%）；固定池受共享队列 + `notify_all` 唤醒风暴拖累。
- 量化工作窃取池的两项真实开销：空闲时每线程每秒 **661 次无效唤醒**（固定池 9.8 次，67 倍），
  空闲 CPU 占用高约 70 倍；长任务扎堆时吞吐仅为固定池的 **1/6**（427ms vs 73ms）。
- 量化提交路径：`submit()` 每任务 **5 次堆分配**，是 `AddTask`（0.06 次）的约 80 倍，
  据此定位纯调度场景的瓶颈在提交端。
- 用 `git show` 导出优化前版本做 **A/B 交替对照压测**（同轮内比值归一化以消除虚拟机环境漂移），
  发现历史提交声称的「不均衡场景 +65%」实测只有 **7%~28%**，据此修正了优化结论。
